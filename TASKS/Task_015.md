# Task 015: MVPコア機能仕上げ — 通知・取引日補正・未完了記録一覧

## 目的

Task 014までで、見送り記録、答え合わせ、振り返り、見送り傾向分析、振り返り検索までの主要体験が成立した。

Task 015では、MVP完成に必要な残りのコア機能として、以下の5つをまとめて実装する。

1. 答え合わせ日が来たことを知らせるOSローカル通知
2. 土日・祝日・休場日に当たった答え合わせ日の取引日補正
3. ホームの「最近のもし株」から、まだ答え合わせ完了していない全記録を見られる一覧
4. 設定タブから、これまでの見送り記録・答え合わせ結果をまとめてリセットできる機能
5. 「最近のもし株」および未完了記録一覧から、見送り記録を1件ずつ削除できる機能

今回のゴールは、

**記録する → 待つ → 通知で気づく → 答え合わせる → 振り返りへ移る**

というMVPの基本サイクルを完成させること。

---

## 画面・データの役割整理

MVPでは記録の状態を以下のように整理する。

### 1. 最近のもし株 / 全記録

まだ答え合わせが完了していない記録を見る場所。

対象：

- 答え合わせ予定日前
- 答え合わせ可能だが未確認
- 結果取得失敗等で未完了

completed記録は表示しない。

### 2. ベル / 答え合わせ

今、答え合わせ結果を確認できる記録を見る場所。

答え合わせ結果の取得・保存に成功した記録は通知対象から外れる。

### 3. 振り返り

答え合わせ結果が保存済みのcompleted記録を見る場所。

---

# Part A: OSローカル通知

## 1. ローカル通知を実装する

Flutterのローカル通知機能を利用し、答え合わせ可能になるタイミングでOS通知を表示する。

Push通知サーバーは今回利用しない。

実装候補：

- `flutter_local_notifications`
- 必要なタイムゾーン対応パッケージ

既存構成と相性のよい一般的な方法を採用する。

## 2. 通知タイミング

答え合わせ対象日の市場取引終了後に通知する。

MVPでは日本株を対象としているため、通知時刻は日本時間の夕方に固定してよい。

推奨初期値：

`17:00 JST`

目的は「その日の終値が取得できる可能性が十分高い時間帯」に知らせること。

15:30ぴったりなど、市場終了直後すぎる時刻にはしない。

## 3. 取引日補正後の日付へ通知を予約する

通知は元の答え合わせ予定日ではなく、Part Bで算出する `effectiveAnswerDate` に対して予約する。

例：

```text
元の答え合わせ予定日：2026/09/13（日）
↓
補正後：2026/09/14（月）
↓
2026/09/14 17:00 に通知
```

土日祝に誤って通知しない。

## 4. 通知内容

1件の場合の例：

タイトル：

`もし株の答え合わせができるよ`

本文：

`三菱UFJフィナンシャル・グループの答え合わせを見てみよう`

複数件が同日にある場合、可能であれば通知をまとめる。

例：

`3件のもし株を答え合わせできます`

MVPでは、同日複数件を1件ずつ通知しても致命的ではないが、同時刻に大量通知が並ばないよう可能な範囲でグループ化を優先する。

## 5. 通知権限

iOSで必要な通知権限を適切にリクエストする。

初回起動直後に唐突に権限ダイアログを出すのではなく、通知機能が必要になる自然なタイミングを優先する。

MVPでは以下のどちらかでよい。

- 初めて見送り記録を保存した後
- 設定画面で通知をONにした時

実装の複雑さとUXを比較して、自然な方法を採用する。

## 6. 通知ON / OFF

既存の設定タブに、最低限以下を追加する。

`答え合わせ通知`

- ON
- OFF

初期値はONでよい。

ただしOS通知権限が拒否されている場合は、アプリ内設定だけONに見えて混乱しないよう状態を分かりやすく扱う。

デフォルト答え合わせ期間の設定機能は今回追加しない。

既存の初期値 `1か月後` を維持する。

## 7. 通知OFF時

通知OFFでも、アプリ内の以下は通常どおり動作する。

- ベルの件数バッジ
- 猫の吹き出し
- 答え合わせ一覧

OS通知だけを止める。

## 8. 通知タップ時の遷移

OS通知をタップするとアプリを開き、可能な範囲で `答え合わせ` 画面へ遷移する。

1件の記録を特定できる通知の場合は、その記録の答え合わせ結果へ直接進めてもよい。

複数件通知の場合は `答え合わせ` 一覧へ遷移する。

アプリが以下の状態でもクラッシュしないこと。

- foreground
- background
- terminatedから起動

## 9. completed後の通知管理

答え合わせ結果の取得・保存に成功しcompletedとなった記録について、不要な未配信通知が残っている場合はキャンセルする。

同一記録に対する通知が重複予約されないようにする。

## 10. 通知予約の再構築

アプリ再起動後も、未完了記録に必要な通知状態を維持する。

必要であれば起動時に未完了記録を読み込み、通知予約を安全に再構築する。

同じ通知を二重予約しないこと。

# Part B: 答え合わせ日の取引日補正

## 11. effectiveAnswerDateを導入する

ユーザーが指定した答え合わせ予定日と、実際に価格取得・通知に使う日付を分ける。

例：

- requestedAnswerDate
  - ユーザーが選択した元の日付
- effectiveAnswerDate
  - 実際の取引日へ補正した日付

元のユーザー設定を破壊しない。

## 12. 土日の補正

requestedAnswerDateが土曜・日曜の場合、次の取引候補日へ繰り越す。

例：

```text
土曜日 → 翌営業日候補
日曜日 → 翌営業日候補
```

## 13. 日本の祝日・市場休場日への対応

日本株市場の休場日を考慮する。

最低限：

- 土日
- 日本の祝日
- 年末年始など東証休場日

を考慮し、次の取引日へ繰り越す。

実装は専用の `MarketCalendarService` 等へ分離する。

画面内へ休日判定ロジックを直書きしない。

## 14. 取引日カレンダーの実装方針

正確性を優先し、将来差し替え可能な構造にする。

例：

- JPXの営業日情報を基にしたローカルデータ
- 利用条件を確認したライブラリ
- Backend側のMarketCalendarProvider

のいずれかを採用してよい。

特定Webページを実行時にスクレイピングして判定する実装は行わない。

## 15. 価格データ不存在時の安全策

effectiveAnswerDateとして取引日と判定したにもかかわらず、Backendで価格データを取得できない場合はcompletedにしない。

その場合は既存の再試行UIを維持する。

市場カレンダーと価格Providerの食い違いで記録を壊さない。

## 16. 既存データとの互換性

Task 015以前の保存済み記録にeffectiveAnswerDateが存在しなくてもクラッシュしない。

読み込み時にrequestedAnswerDateから必要に応じて算出する。

## 17. 開発者メニューとの連携

既存debug build限定の答え合わせ可能化機能を壊さない。

開発用オーバーライドは、本番のrequestedAnswerDate / effectiveAnswerDateを書き換えない既存方針を維持する。

# Part C: 「最近のもし株」から未完了記録の全一覧へ

## 18. ホームの「最近のもし株」は最大3件を維持

ホーム画面では、現在と同じく最近の未完了記録を最大3件表示する。

ホームを長い履歴一覧にしない。

## 19. 「すべて見る」導線

`最近のもし株` セクションに

`すべて見る >`

を追加する。

未完了記録が存在する場合にタップできる。

## 20. 未完了記録一覧画面を追加

新しい画面を追加する。

画面タイトル候補：

`もし株の記録`

または

`見送り記録`

UI全体との自然さを優先してどちらかを採用する。

明確な戻るボタン `<` を表示する。

## 21. 一覧へ表示する対象

completedではない保存済み記録のみ表示する。

含む：

- 答え合わせ予定日前
- 答え合わせ日到来済み・未確認
- 取得失敗で未完了記録が表示される

含まない：

- completed / 振り返り対象

completed記録は `振り返り` タブへ役割を分離する。

## 22. 一覧の並び順

初期表示は新しい記録順とする。

Task 014のような高度なフィルター・検索は今回実装しない。

## 23. 一覧カードの表示内容

最低限以下を表示する。

- 会社ロゴ / 銘柄アイコン（既存表示がある場合）
- 銘柄コード
- 銘柄名
- 見送り価格
- 記録日時
- 見送り理由
- 答え合わせ予定
- 現在の状態

状態表示例：

- `答え合わせまであと12日`
- `明日答え合わせ`
- `答え合わせできます`
- `価格取得を再試行できます`

状態文言は過度に複雑にしない。

## 24. カードタップ

未完了記録カードをタップした場合の挙動：

- 答え合わせ予定日前：記録内容を確認できる簡易詳細、または何もしないでもよい
- 答え合わせ可能：既存の答え合わせフローへ進む
- 取得失敗：再試行可能な答え合わせ画面へ進む

MVPで新しい詳細画面を増やしすぎないことを優先する。

既存画面を再利用できる場合は再利用する。

## 25. 0件時

未完了記録が0件の場合：

`まだ答え合わせ待ちのもし株はありません`

などの空状態を表示する。

completed記録が存在していても、この画面では表示しない。

## 26. ホームへの即時反映

新規記録保存後、再起動せずホームの最近のもし株・全記録一覧へ反映する。

答え合わせ完了後、その記録は再起動せず以下から消える。

- 最近のもし株
- 未完了記録一覧

そして `振り返り` へ表示される。

# Part D: 記録の削除・全記録リセット

## 27. 設定タブに「すべての記録をリセット」を追加

既存の設定タブに、保存済みの見送り記録をまとめて削除できる項目を追加する。

表示例：

`すべての記録をリセット`

この操作は、以下を対象にする。

- 答え合わせ予定前の記録
- 答え合わせ可能な未確認記録
- 価格取得失敗等で未完了の記録
- completed / 振り返り対象の記録
- 答え合わせ結果
- 保存済みの分析元データ
- 対象記録に紐づく通知予約
- 対象記録に紐づくdebug用オーバーライド

つまり、ユーザーがこれまで作成した「もし株」の記録データを初期状態へ戻すための操作とする。

## 28. 全記録リセットは確認ダイアログを必須にする

誤操作を防ぐため、タップしただけで即削除しない。

確認ダイアログ例：

```text
すべての記録を削除しますか？

見送り記録と答え合わせ結果がすべて削除されます。
この操作は元に戻せません。

[キャンセル]  [すべて削除]
```

`すべて削除` は破壊的操作であることが視覚的に分かるデザインにしてよい。

## 29. 全記録リセット後の状態

リセット成功後は以下を即時反映する。

- ホームの「最近のもし株」が0件になる
- ベルのバッジが0件になる
- 猫の吹き出しが通常状態へ戻る
- 未完了記録一覧が空になる
- 振り返り一覧が空になる
- 見送り傾向分析が空状態へ戻る
- 対象となるOSローカル通知予約をキャンセルする
- debug用答え合わせ日オーバーライドを削除する

アプリ再起動を必要とせず、画面へ即時反映すること。

## 30. 「最近のもし株」に1件削除ボタンを追加

ホームの `最近のもし株` に表示される各未完了記録を、1件ずつ削除できるようにする。

削除導線例：

- 小さなゴミ箱アイコン
- `...` メニュー内の `削除`
- スワイプ削除

MVPでは誤タップしにくく、UIを壊さない方法を採用する。

小さすぎるゴミ箱アイコンをカードの主操作と競合する位置へ置かないこと。

## 31. 未完了記録一覧でも1件削除できるようにする

`すべて見る >` から開く未完了記録一覧でも、各記録を1件ずつ削除できるようにする。

ホームと未完了記録一覧で、削除操作・確認文言を可能な限り統一する。

completed記録の削除は今回この1件削除機能の対象外とする。

振り返り側の個別削除は別Taskで検討してよい。

## 32. 1件削除も確認操作を入れる

1件削除時も、誤操作を防ぐため確認ダイアログを表示する。

例：

```text
この記録を削除しますか？

三菱UFJフィナンシャル・グループ
3,515円で見送り

[キャンセル]  [削除]
```

削除後に元へ戻せないことが分かる文言を必要に応じて表示する。

## 33. 1件削除時の関連データ処理

未完了記録を削除した場合、そのrecord idに紐づく以下も削除・キャンセルする。

- OSローカル通知予約
- debug用答え合わせ日オーバーライド
- その記録に紐づく一時的な答え合わせ状態

他の記録へ影響を与えない。

## 34. 1件削除後の即時反映

削除成功後、再起動なしで以下へ即時反映する。

- ホームの最近のもし株
- 未完了記録一覧
- ベル件数
- 猫の吹き出し

削除した記録が答え合わせ可能状態だった場合、ベル件数も正しく1件減らす。

## 35. 削除失敗時

保存削除または関連通知キャンセル等でエラーが起きてもアプリをクラッシュさせない。

記録削除が完了していない場合は、UI上だけ先に消えたように見せない。

エラー表示例：

`記録を削除できませんでした。もう一度お試しください。`

# 通知とアプリ内状態の関係

## 36. 通知は補助導線とする

OS通知が届かない、またはユーザーがOFFにしていても、アプリを開けば正しい状態が確認できること。

状態の正本は端末保存されたSkipRecordと答え合わせ判定ロジックとする。

OS通知の配信有無を記録状態の正本にしない。

## 37. 通知既読とcompletedを混同しない

OS通知をタップしただけでcompletedにはしない。

completedになるのは、Task 011の既存仕様どおり、答え合わせ価格取得・結果保存に成功した時点。

通知はあくまで答え合わせ画面への入口とする。

# UI方針

- クリーム系背景
- 緑を基本カラー
- 大きめの角丸
- 柔らかいゴシック系
- 明朝体っぽい細い文字は使わない
- 猫キャラクターの既存世界観を維持する
- 通知設定を複雑にしない
- 未完了一覧を情報過多にしない
- ホームは最大3件のままスッキリ維持する
- iPhoneの小さい画面でも自然にスクロールできる

- Task 014までの検索・記録・答え合わせ・振り返り・分析を壊さない
- 通知機能と記録状態を密結合させない
- 通知OFFでもアプリ内答え合わせは正常に動作させる
- requestedAnswerDateとeffectiveAnswerDateを分離する
- 市場営業日ロジックをUIへ直書きしない
- completed記録を未完了一覧へ表示しない
- completed時に最近のもし株 / 未完了一覧 / ベル / 振り返りが整合する
- 古い保存データとの後方互換を維持する
- debug開発者メニューを壊さない
- 全記録リセット・1件削除はいずれも確認操作を必須にする
- 1件削除は未完了記録のみを対象にし、completed記録は今回対象外とする
- 削除時は対象record idに紐づく通知予約・debugオーバーライドも整理する
- 削除・リセット後はホーム / ベル / 猫 / 未完了一覧 / 振り返り / 分析の表示整合性を即時更新する
- Task 015の範囲外を先回り実装しない

# テスト

最低限以下を確認する。

## 通知

- 通知ON時にローカル通知を予約できる
- 通知OFF時に新しい通知を予約しない
- 通知OFFでもベル・猫・答え合わせ一覧が機能する
- 通知権限拒否時にクラッシュしない
- 同一記録の通知が重複予約されない
- completed後に不要な通知が残らない
- 通知タップでアプリを開ける
- 通知タップから答え合わせ一覧または対象結果へ遷移できる

## 取引日補正

- 平日の通常取引日はその日をeffectiveAnswerDateにできる
- 土曜日を次の取引日へ補正できる
- 日曜日を次の取引日へ補正できる
- 日本の祝日を次の取引日へ補正できる
- 年末年始等の市場休場日を補正できる
- requestedAnswerDateは元の値を維持する
- 古い保存データでも補正計算できる
- 価格取得失敗時にcompletedにならない

## 未完了記録一覧

- ホームは最近の未完了記録を最大3件だけ表示する
- `すべて見る` から未完了記録一覧へ遷移できる
- completed記録が一覧へ表示されない
- 答え合わせ予定日前の記録が表示される
- 答え合わせ可能な未確認記録が表示される
- 取得失敗中の未完了記録が表示される
- 状態文言が適切に表示される
- 答え合わせ完了後に再起動なしで一覧から消える
- completed記録は振り返りへ移る
- 0件時に空状態が表示される

## 削除・リセット

- 設定タブに `すべての記録をリセット` が表示される
- 全記録リセット前に確認ダイアログが表示される
- キャンセルした場合はデータが削除されない
- 全記録リセットで未完了・completedを含む保存済み記録が削除される
- 全記録リセット後にベルが0件になる
- 全記録リセット後に猫の吹き出しが通常状態へ戻る
- 全記録リセット後に振り返りが空になる
- 全記録リセット後に見送り傾向が空状態へ戻る
- 全記録リセット時に関連通知予約がキャンセルされる
- ホームの最近のもし株から1件削除できる
- 未完了記録一覧から1件削除できる
- 1件削除前に確認ダイアログが表示される
